# PRD: `opencode-memory` v2.1 记忆机制演进规划

> 版本目标：`2.1.0`（基于 `2.0.0` 本地-only OpenCode V2 架构）  
> 调研依据：`docs/dev/research/hermes-openclaw-memory-mechanism.md`  
> 现状基线：`docs/architecture.md`、`apps/plugin/src/`（`2.0.0-rc.1`）

---

## 1. 背景与核心问题

在完成 Hermes Agent 与 OpenClaw 记忆机制的一手源码调研后，结合 `opencode-memory` 当前源码与已存在的 GitHub Backlog（`#28`–`#37`），识别出制约成本、召回精度与长期可用性的 5 个核心问题：

1. **KV Cache 命中率受损（注入未冻结）**
   - `ctx.session.hook("context")` 每次模型请求都从磁盘重读 `MEMORY.md` / `IDENTITY.md` / `USER.md` / 项目 `MEMORY.md`，并与静态指令及动态 `## Memory Reminder` 拼接为单一 `SystemPart`。
   - 会话中途写入 `daily` 或触发提醒都会破坏整个系统提示词前缀缓存。
2. **上下文预算粗放（1000 行 ≠ 稳定 Token 预算）**
   - `checkLineLimit()` 仅对 `MEMORY.md` 做 `1000` 行校验；`USER.md`、`IDENTITY.md` 无上限；写入返回无容量占用率提示，模型缺乏主动精简信号。
3. **纯向量检索在代码场景精度不足，且缺乏时间维度**
   - `FileSearcher.semanticSearch()` 仅按余弦相似度排序；精确符号（环境变量、端口、错误码、类名）召回弱；`daily/` 日志没有时间衰减，历史日志容易压过近期记录；同一文件高重叠 chunk 容易占满结果集。
4. **缺少写入来源边界（Provenance）**
   - 外部网页或工具检索结果可直接通过 `memory(action="write", target="memory")` 写入每轮自动注入区，存在上下文污染风险。
5. **长会话上下文压缩前无兜底，且缺少从 `daily/` 到 `MEMORY.md` 的整理机制**
   - 若会话全程未调用 `memory` 工具便触发上下文压缩（Compaction），期间产生的决策与踩坑极易丢失；同时 `daily/` 长期积累后缺乏可控的蒸馏归纳流程。

## 2. 产品定位与非目标（Non-Goals）

### 定位原则

- **Markdown + Git 仍是唯一真源（SSOT）**：Vectra 及新增词法索引始终保持“可删除并全量重建的派生缓存”。
- **取两家之长，适配开发者本地场景**：吸收 Hermes 的「硬预算 + 快照缓存纪律」与 OpenClaw 的「混合检索 + 时间衰减 + Provenance 边界 + 压缩前兜底」，去掉重型后台守护进程。

### 明确不做的事（Non-Goals）

- ❌ **不引入后台 Cron 守护进程（Dreaming Daemon）**：开发者本地场景下，未授权后台改写 `MEMORY.md` 不可控且浪费 Token；改为显式 `/memory-consolidate` 命令。
- ❌ **不重建重型 `providers/` 多后端抽象层**：`918218b` 已基于 YAGNI 清理过冗余 provider 抽象；继续保持单引擎本地实现，仅保留窄接口隔离检索细节。
- ❌ **不做多记忆后端并行路由**：同一时刻只维护一套本地索引引擎。

## 3. 里程碑规划与验收标准

### M0：`2.0.0` 稳定版基线收口（前置，不掺杂 2.1 新特性）

- **范围**：收敛既有发布阻塞项 `#26`、`#28`（Windows 路径与项目 stale 索引）、`#33`（JSONC 解析）、`#34`（文件/索引并发锁与单例消除）；核对关闭已完成的 `#27`、部分 `#35`。
- **目标**：发出可靠的 `2.0.0` 稳定版，作为 2.1 演进的并发与配置安全基线。

### M1：注入缓存与字符预算体系（降本稳延迟）

- **目标**：
  1. **SystemPart 分层 + Session 级冻结快照**：静态指令、记忆快照、动态提醒拆分为独立 `SystemPart`；记忆正文在 session 生命周期内冻结，仅在**本会话修改了会注入的文件**或**发生压缩**时失效。
  2. **分目标字符预算 + 占用率回显**：替代单一 1000 行粗限制，在写入返回中附带超简洁占用提示（如 `Budget: 1,420/6,000 chars (24%)`）。
  3. **单次调用腾挪能力**：支持先删后写（`replace_timestamps` / 批量删除）且仅对终态做预算校验，避免满容时多轮重试。
- **验收标准**：
  - [ ] 会话内连续请求（无注入文件变更时）不再重复读取磁盘，输出文本字节完全一致。
  - [ ] 仅写 `daily` **不会**触发注入快照失效（保住前缀缓存）。
  - [ ] 超过字符预算时拒绝写入并返回已有条目时间戳摘要；未超限但 ≥ 85% 时返回精简预警。

### M2：混合检索、时间衰减与可信边界（提效防污染）

- **目标**：
  1. **Hybrid 混合检索**（衔接 `#29`、`#30`、`#31`、`#32`、`#36`）：切片注入标题上下文、先比对 Hash 再 Embedding、词法 BM25 + Vectra 向量融合排序、`period`/`scope` 前置过滤、`list` 感知项目作用域。
  2. **分层时间衰减 + 去重**：`MEMORY.md` / `USER.md` / `IDENTITY.md` 永不衰减；`daily/YYYY-MM-DD.md` 按 30 天半衰期衰减，且 **`minScore` 在衰减前判定**；结果做轻量 MMR/去重。
  3. **轻量 Provenance 边界**：通过时间戳注释扩展可选 `origin` 属性（`owner | agent | external`），自动注入跳过 `external` 条目。
- **验收标准**：
  - [ ] 精确符号（环境变量、报错码、文件名）在混合检索中稳定命中前排。
  - [ ] 同等语义相关性下，近期 `daily` 排序高于半年前 `daily`；`MEMORY.md` 不受时间衰减惩罚。
  - [ ] 标为 `origin: external` 的条目不会出现在 `session.hook("context")` 的自动注入文本中。

### M3：生命周期闭环（Compaction Flush + `/memory-consolidate`）

- **目标**：
  1. **压缩前自动沉淀（Compaction Flush）**：利用 OpenCode V2 `ctx.session.hook("compaction")` 在对话历史被压缩前提取未落盘的关键决策/踩坑，自动追加到当前项目（或全局）`daily/YYYY-MM-DD.md`。
  2. **按需蒸馏命令 `/memory-consolidate`**：用户主动触发，汇总近期 `daily/` 并结合当前 `MEMORY.md` 预算进行去重、合并与过时条目清理，所有改动经 Git 留痕。
- **验收标准**：
  - [ ] 长会话触发 compaction 时，每个压缩周期最多自动沉淀一次 `daily`，且失败/超时绝不阻塞 OpenCode 压缩主流程。
  - [ ] 执行 `/memory-consolidate` 可将近期 `daily` 中的可复用结论提炼入 `MEMORY.md` 并受 M1 字符预算约束。
